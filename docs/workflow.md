# 작업 규칙

백엔드의 `docs/workflow.md`와 동일한 개발 절차를 적용합니다.

## 개발 원칙

- YAGNI를 지키며 현재 필요한 기능만 구현한다.
- 불필요한 fallback, 과한 일반화, 미리 만든 확장 포인트는 넣지 않는다.
- 실제 API와 서버 권한을 기준으로 구현하며 미구현 기능을 샘플 데이터로 동작하는 것처럼 표시하지 않는다.
- 복잡도를 높이는 구조보다 단순하고 읽기 쉬운 구조를 우선한다.

## 코드 스타일

- 변수와 함수는 이름만으로 대상, 역할, 동작을 이해할 수 있도록 의도가 명확한 이름을 사용한다.
- 의미를 추측해야 하는 축약어와 단일 문자 변수, 불분명한 함수명을 피한다.
- boolean은 `isApprovedMember`, `canCreateTask`처럼 판단 조건을 표현한다.
- 코드 설명이 필요할 때만 짧게 주석을 추가한다.
- 기존 스타일과 충돌하지 않는 한 가독성을 우선한다.

## 커밋·브랜치 규칙

- 브랜치는 영어 `feature/<기능명>#<이슈번호>` 형식으로 작성한다.
- 커밋은 기능 단위로 분리하고 메시지 내용은 한국어로 작성한다.
- prefix는 `feat:`, `refact:`, `fix:`, `chore:`, `test:`만 사용한다.
- `feat:`는 새 기능, `refact:`는 동작 변화 없는 구조 개선, `fix:`는 버그 수정, `chore:`는 문서·설정·빌드, `test:`는 테스트 변경에 사용한다.

## 이슈·PR·작업 흐름

1. 최신 `main`을 기준으로 이슈를 템플릿에 맞춰 먼저 생성한다.
2. 이슈 번호가 포함된 브랜치를 만들고 기능별로 구현·커밋한다.
3. 관련 테스트와 빌드를 확인한다.
4. PR은 저장소 템플릿에 맞춰 변경 내용·검증·특이사항을 작성한다.
5. PR 제목은 접두사 없이 핵심 내용을 적고 이슈 제목은 템플릿 접두사를 유지한다.
6. 리뷰는 필요한 범위만 반영하고, 머지 후 다음 작업은 최신 `main`에서 시작한다.

구성 관련 작업은 `chore` 라벨을 사용한다. 코드와 문서가 따로 놀지 않도록 정책·예외·흐름 변경을 `docs`에도 반영한다.

## 테스트 규칙

- 가능한 한 given / when / then 구조로 작성한다.
- 프론트에서는 단위 테스트를 `*.test.js`, 브라우저 테스트를 `*.spec.js`로 구분한다.
- 테스트 제목은 한글로 작성한다.
- 구현을 그대로 복제하는 테스트보다 권한, 충돌, 실패 경로와 실제 사용자 흐름의 회귀를 검증한다.
- 테스트 응답을 사용한 브라우저 검증과 실제 서버·계정 검증을 구분해 기록한다.

## 의사결정 기준

단순한 해결책부터 검토한다. 현재 목표에 직접 기여하지 않는 기능은 미루고 성능·안정성·유지보수성은 실제 사용 경로를 기준으로 판단한다.
